# Medical AI Chat POC

Arabic and English chat with conversation memory, structured replies, and up to
five symptom follow-up questions, personalized using an optional medical profile.
After the second follow-up answer, chat replies also request general medical information using Gemini's built-in
Google Search tool, with provider-supplied citations. All application code is in `main.py`.
Use synthetic symptom messages. This demonstration is not a validated medical
triage tool. Emergency guidance and matching reported facts to final demo rules
depend on model interpretation; these rules have not been clinician-reviewed.

## Start the app

Run these commands in PowerShell from this project folder:

```powershell
uv sync
Copy-Item .env.example .env
```

Create a Gemini API key at https://aistudio.google.com/apikey and ensure your API
project has available quota and access to the configured model. Open `.env` in
your editor and put the key after `GEMINI_API_KEY=`. Keep the key on the server;
do not share it in chat, commit it, or send it to React.

Your Gemini configuration should look like this:

```env
GEMINI_API_KEY=your_gemini_key_here
GEMINI_MODEL=gemini-3.8-flash
```

The service uses Google's `google-genai` SDK. Model availability depends on your
API project; the model name can be changed in `.env`. See Google's current
[model list](https://ai.google.dev/gemini-api/docs/models).

Then start the server:

```powershell
uv run uvicorn main:app --reload
```

After editing `.env`, restart the server. Copy `.env.example` only on first setup
so you do not overwrite an existing key.

## Test conversation memory

In Swagger, send the first symptom message with `session_id: "demo123"`.
Read Gemini's question, then send an answer with the **same session ID**:

```json
{
  "session_id": "demo123",
  "message": "It started gradually."
}
```

Use an answer that matches the actual question Gemini asked. The model now
receives the first symptom message, its previous question, and your new answer.
Continue using `demo123` for this conversation. Use a different ID, such as
`demo456`, to start a new conversation with no previous messages.

The backend should create one unique session ID per conversation and reuse it
for all answers in that conversation. The API echoes the ID in each response.

Memory lives in a Python dictionary. Restarting the server or saving code while
`--reload` is active clears it. Run one server worker for the local demo; multiple
workers do not share this dictionary. Failed provider requests do not save the
new user message or an incomplete answer; retry with the same session ID and
message. Failed requests also leave the question counter unchanged.

## Test the follow-up limit and structured summary

1. Start a fresh session, for example `summary-demo`, with a symptom message.
2. Answer each actual question using that same session ID.
3. Each symptom follow-up increases `followup_count`; memory questions and
   unrelated exchanges do not. The model indicates whether its reply is a
   symptom question, and Python maintains the counter.
4. After Gemini asks its fifth follow-up, answer it. The next response must have
   `status: "assessment"`, a non-null `assessment`, and no more questions.
5. Messages after a summary update the summary instead of restarting questioning.

The first symptom request normally returns question 1; four subsequent answers
normally produce questions 2–5; the answer to question 5 produces the summary.
Change `MAX_FOLLOWUPS` near the top of `main.py` to adjust the demonstration limit.

An example summary response (illustrative, not a patient assessment):

```json
{
  "session_id": "summary-demo",
  "status": "assessment",
  "message": "Contact a healthcare professional or local medical advice service to clarify the next step.",
  "followup_count": 5,
  "max_followups": 5,
  "urgency": "unable_to_determine",
  "assessment": {
    "symptom_summary": "The patient reports a headache since this morning.",
    "possible_causes": [],
    "recommended_action": "Contact a healthcare professional or local medical advice service to clarify the next step.",
    "classification_reason": "The available information or demo rules are insufficient to determine urgency.",
    "rule_id": "unknown",
    "actions_now": [
      {
        "instruction": "Contact a healthcare professional or local medical advice service to clarify the next step.",
        "source_ids": ["nhs_advice"]
      }
    ],
    "warning_signs": ["If life-threatening symptoms appear, seek emergency help immediately."],
    "limitations": [
      "This is preliminary guidance, not a diagnosis or validated triage assessment.",
      "Demo rules are limited and not clinician-reviewed. The model interprets answers and can make mistakes; no detected alert does not establish safety."
    ]
  },
  "sources": [{"id": "nhs_advice", "title": "NHS: Getting medical advice", "url": "https://www.nhs.uk/nhs-services/urgent-and-emergency-care-services/when-to-use-111/"}]
}
```

During questioning, urgency remains `unable_to_determine`. Final responses can
use any of the five labels described below, with actions and source references.
General search-supported information appears in `medical_information`, separate
from the final actions. An empty list does not imply safety.
The existing model-based emergency warning can end questioning early and suggest
immediate emergency help; it is provisional, not a validated safety rule.
Avoiding repeated questions is instructed through the prompt and full history;
there is no semantic duplicate-question checker in this simple POC.

## Test medical profile personalization

Start a new session in Swagger with a synthetic profile:

```json
{
  "session_id": "profile-demo",
  "message": "I have a headache since this morning.",
  "medical_profile": {
    "age": 25,
    "chronic_conditions": ["hypertension"],
    "medications": ["amlodipine"],
    "allergies": [],
    "medical_history": []
  }
}
```

Gemini receives these details when selecting relevant questions. It is instructed
to avoid asking for already supplied details unless clarification is needed.
The particular question is generated dynamically, so do not expect fixed wording.

To check the profile is remembered, omit it from the next request:

```json
{
  "session_id": "profile-demo",
  "message": "Which medication is listed in my medical profile?"
}
```

The expected response mentions amlodipine, without increasing the follow-up count.
Repeat the question with a new session ID and no profile: it should not know the
medication from `profile-demo`.

Profile behavior for backend developers:

- `medical_profile` is optional; conversations without a profile still work.
- Omitted fields or explicit `null` fields mean unknown. An explicit `[]` means
  the backend reports no entries for that field.
- Age must be an integer between 0 and 130 for this demo. The four other fields
  accept lists of non-empty strings, in Arabic or English.
- Sending a new profile object replaces the previous object, including fields
  omitted from the replacement. This is a full replacement, not a partial merge.
- Omitting the whole profile or sending `medical_profile: null` reuses the stored
  profile. Send `medical_profile: {}` to reset all profile fields to unknown.
- A profile change is saved only after a successful AI reply. If a request fails,
  retry with the same message and profile.
- Profile changes do not reset conversation history or the follow-up counter.
- If the profile conflicts with a patient's message, Gemini is instructed to
  clarify the conflict rather than assuming either version is correct.

The profile is sent as labeled data in a user-context message; it is not placed
inside the system instructions. Current profile context is rebuilt each turn,
so old profile snapshots are not repeatedly sent as separate profile records.
Profile personalization affects the final decision but does not establish
clinical safety or a diagnosis.

## Backend integration

Send an HTTP POST to `http://127.0.0.1:8000/ai/chat` with
`Content-Type: application/json`. Both the request and response contain
`session_id` and `message`. Read the response's `detail` field when an error occurs.
Use `status` to choose between displaying a chat reply (`question`) and displaying
the symptom summary (`assessment`). `question` means the information-gathering
stage; a memory answer or greeting in that stage may not contain a new question.
Use `followup_count` and `max_followups` to display progress.
For example, missing API configuration returns HTTP 503; invalid input returns
HTTP 422. Use the AI server's reachable address if the backend runs elsewhere.

The intended connection is React → your team's backend → this AI API.

## How main.py works

- `MedicalProfile` validates the optional medical data.
- `ChatRequest` validates and trims the session ID and incoming message.
- `INSTRUCTIONS` controls language and basic assistant behavior.
- `sessions` stores separate conversations, profiles, and question counts by session ID.
- `ModelReply` describes the JSON Gemini must generate; Pydantic validates it.
- `ask_gemini()` sends the current profile, full history, and stage, then checks the response.
- `chat()` loads history, adds the new message, and saves successful replies.
- `search_medical_information()` requests Google Search and maps cited statements to provider URLs.
- `build_final_assessment()` matches checked source passages to a demo rule;
  Python maps that rule to a label and supplies cited actions and warning signs.
- Python controls the question limit and refuses self-care when required checks are missing.
- A small lock keeps simultaneous requests for the same session in order.
- Provider failures return an HTTP error instead of a made-up answer.

Search is a source preference, not a strict domain restriction. Final actions
use the separately checked NHS passages in `GUIDANCE`, not arbitrary web snippets.

## Test built-in web search

No additional key or package is needed. The configured Gemini model and API
project must support Google Search grounding. Search can add latency and consume
additional provider quota. See the official [Google Search guide](https://ai.google.dev/gemini-api/docs/generate-content/google-search).

1. Start a fresh session such as `search-demo` with a synthetic symptom message.
2. Answer the first and second actual follow-up questions using that session ID.
   The reply to your second answer normally asks question three and also requests search.
3. In that response, check `search_status`:
   - `grounded`: top-level `medical_information` has cited statements.
   - `unavailable`: search failed, was blocked, or supplied no usable citation metadata.
   - `not_requested`: before the second answer, unrelated exchanges, or emergency guidance that skips search.
4. Each information item's `source_ids` refers to an `id` in the top-level
   `sources` list. Display those links next to that item; do not attach them to
   unrelated symptom summaries or recommendations.
5. Check the links yourself. Some are Google grounding redirects, which is normal.

Search starts after the second follow-up answer, refreshes on subsequent symptom
answers, and also runs on non-emergency summaries. The first symptom request and
first follow-up answer do not search. Memory questions and greetings in the
question stage do not trigger search. Search receives actual patient messages and
the current profile, plus any unconfirmed AI visual observations. Raw image bytes
are sent to the chat model; the separate search call receives text only. Change
`SEARCH_AFTER_FOLLOWUPS` in `main.py` to adjust the start point.
Search failures do not discard a successful chat reply or symptom summary.
The response then has `search_status: "unavailable"` and no cited information.
The initial structured chat call must still succeed.

NHS (`nhs.uk`), MedlinePlus (`medlineplus.gov`), and WHO (`who.int`) are preferred
in the search prompt. Gemini may use other websites. Returned URLs come from
the provider's citation metadata; their presence does not prove their medical
claims are correct or that the preferred-domain restriction was followed.
The code does not infer a URL's destination from its title.

Backend/frontend integration: show top-level `medical_information` as general
medical information, separate from the patient's symptom summary. When present,
display Google's `search_suggestions_html` according to Google's [grounding
display requirements](https://ai.google.dev/gemini-api/docs/grounding/search-suggestions).
Keep provider HTML isolated from your application UI (for example in a sandboxed
iframe), rather than injecting it directly into the page. Swagger shows the raw HTML.
Patient messages, optional photos, and normal chat replies are stored in conversation memory;
search output is not stored as a previous patient statement.

## Optional photo input (same endpoint)

Gemini is multimodal: the same model processes text and images. We use inline
image bytes through the existing SDK, without training a vision model or adding
packages. See Google's [image input guide](https://ai.google.dev/gemini-api/docs/generate-content/image-understanding).

`POST /ai/chat` accepts an optional `image` object containing:

- `mime_type`: `image/jpeg` or `image/png`.
- `base64_data`: the raw base64 string, without the `data:image/...;base64,` prefix.

Use one photo per request, at most 2 MiB. A session can retain at most 8 MiB of
photos. Invalid encoding, unsupported types, or a mismatched file header return
422. File header checks are basic; a corrupt file may still be rejected by Gemini.
The cumulative session limit returns 413. Keep using synthetic demo
images without patient identifiers. Photos are sent to the Gemini API and retained
in temporary session memory; no image files are written to disk.

To generate a request for Swagger, choose a demo PNG file and run this in PowerShell
(replace the path with your file). For JPEG, change `mime_type` to `image/jpeg`:

```powershell
$demoPhotoPath = 'C:\path\to\demo-photo.png'
$demoPhotoBytes = [System.IO.File]::ReadAllBytes($demoPhotoPath)
$demoRequest = @{
    session_id = 'photo-demo-1'
    message = 'This area of skin has been itchy since yesterday. What can you observe?'
    image = @{
        mime_type = 'image/png'
        base64_data = [Convert]::ToBase64String($demoPhotoBytes)
    }
}
$demoRequest | ConvertTo-Json -Depth 5 | Set-Clipboard
```

Open `/docs`, choose **Try it out** on `/ai/chat`, paste the JSON, and execute.
Swagger uses a JSON request; it does not show a file picker for this endpoint.
The frontend/backend team can convert a selected file to base64 and send this
same JSON structure. If using a browser FileReader data URL, strip the prefix
before assigning `base64_data`. The Gemini key stays on the AI server.

Check `image_observations` in the response:

- `observed`: brief descriptions of visible features, without a confirmed diagnosis.
- `unclear`: the photo is not clear enough; observations are empty and a limitation is provided.
- `unsupported`: unrelated images, X-rays, scans, or lab reports are outside this photo demo.
- `null`: this conversation has no image.

Continue answering with the same session ID; omit `image` from later requests.
Earlier photos stay in context so you do not need to resend them. A newly supplied
photo becomes the latest image considered for `image_observations`. The model uses
visual observations for follow-up questions and labels them separately in the
summary. Image observations do not establish a diagnosis or clinical safety.
Photos alone cannot justify a self-care classification.

Manual checks: try a visible skin photo, a blurred photo, and an unrelated object.
Also send invalid base64 to check the 422 response. These classifications are
generated by the model and require live testing; local mocked tests only verify
the API wiring, validation, and memory behavior.

## Final decision and actions

Final responses now include one of these preliminary urgency labels:

| Label | Next step |
| --- | --- |
| `emergency` | Immediate local emergency help. |
| `urgent_medical_attention` | Urgent assessment today. |
| `routine_consultation` | Arrange a medical appointment. |
| `potentially_self_care` | Initial supported self-care, with escalation advice. |
| `unable_to_determine` | Explain uncertainty and obtain professional advice. |

`assessment` contains `classification_reason`, `rule_id`, `actions_now`,
`seek_help_if`, and `possible_explanations`. Actions, warnings, and possible
explanations have `source_ids` pointing to top-level `sources` when individually
supported. Generated steps use `source_ids: []`; references are not automatically
attached to unverified model wording. `possible_causes`
and `warning_signs` remain available as plain-text lists for existing clients.
Explanations are explicitly unconfirmed. No medications or dosages are supplied.

General chat accepts any symptom. Final demo rules currently cover headache,
cold-like symptoms, and itchy skin. Unmatched complaints use the existing separate
guidance generator, falling back to `unable_to_determine` if it fails. Warning signs can cause an
early model emergency alert for other complaints, too. A model alert yields
`emergency` and `rule_id: "model_emergency_alert"`, without waiting for search
or an extra classification request. It is not validated triage.

At a non-emergency summary, an additional Gemini call interprets the conversation
against the short, checked source passages in `GUIDANCE` and generates 3 to 6
ordered first-aid steps in the user's language. This uses the same classification
call, without an additional provider request. Python maps the rule ID to an urgency
label, applies the existing checks, and returns the generated steps through
`assessment.actions_now`. Their source IDs are empty because individual generated
claims have not been verified. Emergency actions remain predefined so an early
emergency alert does not wait for another generation request. Missing or incomplete
steps use the existing predefined actions. The model never supplies source URLs.
Evidence quotes must occur in patient
messages; this check does not prove that the model interpreted their meaning
correctly. Handling negation and conflicts still depends on the model.

Self-care requires all five model-extracted checks to be explicitly true: known
adult age, mild short-duration symptoms, relevant warning signs explicitly denied,
relevant risks checked, and no conflicting or concerning information. Unknown
checks do not pass. Known childhood, a chronic condition, current medication,
relevant medical history, or an unclear/unsupported photo blocks self-care in this
conservative demo. A five-question limit is not proof these checks are satisfied.

Checked NHS passages and rule/action definitions are in `main.py`. They were
checked on 2026-10-09 and need maintenance as guidance changes. NHS services and
numbers are UK-specific; the POC uses generic local-care wording and does not
infer the user's country. Rules are limited and not clinician-reviewed.

If classification fails or returns invalid data, the app still returns the
summary with `unable_to_determine`. A failed web search may leave
`search_status: "unavailable"` while final actions still have checked NHS sources.
The presence of `sources` alone therefore does not prove live search ran.

To test, use a new synthetic session, provide a profile, and answer each actual
question. Try a mild, short-duration complaint with explicit risk/warning-sign
answers; a recurring headache; a headache with vomiting; a headache after a recent
head injury; and an unrelated complaint with missing history. Labels must follow
the reported facts, not the name of the test. Check action/source ID mappings and
that self-care is refused when required information is unknown. Local mocked
classification tests verify wiring and fallbacks; live clinical performance is
not established. Run the local generation/fallback regression checks from `backend`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```
